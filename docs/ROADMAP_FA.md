# رودمپ متن‌باز Attestara

هدف، سورس کامل Apache-2.0 و اجرای محلی بدون حساب پولی/ابری، دامنهٔ عمومی یا کلون پروژهٔ دیگر است. `npm run setup` و `npm start` اکنون وب و فرایند Go محلی را آماده و اجرا می‌کنند. مرورگر سلامت و نسخهٔ واقعی فرایند را نشان می‌دهد؛ ارزیابی دامنه‌ای هنوز پیاده نشده است. Node 24.19.0، npm 11.9.0 و Go 1.27.2 روی Linux x86_64 پیش‌نیازند.

در plans/commits برای هر C01 تا C40 یک کارت با مسیر فایل‌ها، گام‌های دقیق، پیش‌نیاز، منابع، سخت‌افزار، دادهٔ آزمایشی و مجوز، حالت خطا، فرمان آزمون، شواهد و بازگشت وجود دارد. فرمان‌های وابسته به موتور آینده صریحاً علامت خورده‌اند.

- C01–C06: قرارداد استفاده، نسخه‌های قفل‌شده، موتور واقعی، قرارداد داده، ذخیره‌سازی و CI.
- C02 نسخه، هش، منبع رسمی و مجوز ابزارها را ثبت و صحت منابع را بررسی می‌کند. Go از سورس رسمی قابل ساخت است؛ OPA و ابزارهای Syft/Grype اختیاری هستند. این بررسی، تأیید اجرای موتور محصول نیست؛ جزئیات در `docs/engineering/RESOURCE_LOCK.md` و شواهد C02 ثبت می‌شود.
- C03 چرخهٔ ساخت/اجرا/خاموشی و health را با خطاهای صریح، restart و آزمون crash/cancellation پوشش می‌دهد؛ این سلامت، تأیید نتیجهٔ امنیتی یا بازیابی داده نیست. جزئیات در `docs/engineering/ENGINE_LAUNCH.md` و شواهد C03 ثبت می‌شود.
- C04 قرارداد نسخهٔ یک و validator واقعی Go را با fixtureهای مثبت/منفی، محدودیت اندازه و لغو اجرا می‌کند؛ این یک کتابخانه است و اجرای policy، بررسی امضا، API دامنه یا دوام داده را تأیید نمی‌کند. جزئیات در `contracts/README.md` و شواهد C04 ثبت می‌شود.
- C05 کتابخانهٔ مخزن فایل محلی با قفل تک‌نویسنده، ثبت اتمیک، شناسهٔ پایدار عملیات و بازیابی پس از قطع فرایند را اضافه می‌کند. این مرحله API یا هویت خصوصی اضافه نمی‌کند؛ خطای کمبود دیسک به‌صورت کنترل‌شده تزریق می‌شود. جزئیات و حدود اثبات در `docs/architecture/STORAGE_PROOF.md` و شواهد C05 است.
- C06 ساخت، تحلیل و اجرای تست‌های واقعی C03–C05 را در CI موتور الزامی می‌کند؛ نبودن بسته یا تست‌های نماینده خطاست. fixtureهای موجود قرارداد و ذخیره‌سازی دوباره استفاده می‌شوند. بررسی اعتماد امضاکننده و اعتبار نسخه‌های قدیمی هنوز تأیید نشده‌اند؛ جزئیات در `docs/engineering/ENGINE_TESTS.md` و شواهد C06 ثبت می‌شود.
- C07 برای هر فایل شواهد یک envelope نسخه‌دار با digest سوژه، نام و نسخهٔ ابزار، هش مستقل پیکربندی و مشخصات فایل C04 تعریف می‌کند. این مرحله قرارداد JSON ورودی C04 را تغییر نمی‌دهد و provider یا workflow کامل را اجرا نمی‌کند.
- C08 manifest نسخهٔ یک C04 و بایت‌های واقعی فایل‌ها را در یک کتابخانهٔ Go بررسی می‌کند؛ فایل گمشده، مسیر تکراری، اندازه یا digest ناهماهنگ رد می‌شود. نتیجه همچنان نامطمئن است و این مرحله امضا، authority نسخه‌ها، API یا رابط وب را پیاده نمی‌کند.
- C09 reader فقط‌خواندنی ZIP را به C08 وصل می‌کند: manifest.json در ریشه، سقف ورودی ۱۰۰ MiB، سقف مجموع دادهٔ بازشده ۱۰۰ MiB و ۲۰۰۰ فایل. مسیر نامعتبر، symlink، نام تکراری و بمب فشرده‌سازی رد می‌شوند؛ فایل استخراج یا اجرا نمی‌شود و API/وب یا ثبت پایدار جدیدی اضافه نمی‌شود. manifest نیز جداگانه سقف JSON موجود C04 را دارد.
- C10 آداپتر فقط‌خواندنی CycloneDX JSON 1.7 را با اعتبارسنجی کامل schema پین‌شده و آفلاین اضافه می‌کند؛ بایت‌های اصلی حفظ می‌شوند و نسخه‌های دیگر رد می‌شوند. تأیید schema به معنی اعتبار امضا یا اعتماد به تولیدکننده نیست. API، رابط وب و واردسازی پایدار در این دامنه نیستند.
- C11 آداپتر خواندنی SPDX 3.0 را برای بسته‌ها و روابط وابستگی به نمایش نرمال CycloneDX 1.7 تبدیل می‌کند؛ IDها حفظ و نوع‌های نامشخص رد می‌شوند. این زیرمجموعه اعتبارسنجی کامل استاندارد، اعتماد امضا یا import پایدار را ادعا نمی‌کند.
- C12 گزارش JSON موجود Grype را در کتابخانهٔ Go به یافته‌های typed تبدیل می‌کند و نسخهٔ scanner و زمان ساخت DB را نگه می‌دارد. نبود فرادادهٔ feed CVE وضعیت `unknown` است؛ این مرحله scanner را اجرا نمی‌کند و API، رابط وب یا import پایدار ندارد.
- C13 عبارت‌های مجوز SPDX را با کاتالوگ قفل‌شدهٔ مشترک C10 تحلیل می‌کند؛ شناسهٔ شناخته‌شده فقط `recognized` و دادهٔ ناشناخته یا مرجع سفارشی `review` است. عبارت خراب خطای typed می‌دهد و `OR` به‌تنهایی نیازمند بازبینی نیست. هیچ نتیجهٔ compliance، API یا رابط وب از این مرحله نتیجه نمی‌شود.
- C14–C26: قابلیت‌های تخصصی بعدی همین پروژه همراه آزمون و اتصال واقعی وب.
- C27–C30: امنیت، ظرفیت اندازه‌گیری‌شده، سلامت موتور، نصب از کلون، انجام کار اصلی و بازیابی. **C30 نخستین نقطهٔ قابل بهره‌برداری محلی است**، پس از تأیید واقعی همهٔ این موارد.
- C31–C38: بستهٔ کامل موتور/وب و سورس، مجوزها، نصب/میزبانی اختیاری، UX، مستندات، ارتقا و تکرار مستقل نصب و رفع موانع.
- C39–C40: کنترل شواهد انتشار و نصب نسخهٔ واقعاً منتشرشده. **C40 پایان نسخهٔ کامل متن‌باز v1 است.**

ایجنت از AGENTS.md و قرارداد اجرا شروع می‌کند و با `npm run plan -- next` کار بعدی را می‌گیرد. هیچ آزمون اجرا‌نشده یا قابلیت ناقصی انجام‌شده ثبت نمی‌شود. محدودیت دائمی schema دیتابیس، migration، .env و Dockerfile برقرار است.


### دامنه C14

ارزیاب داخلی Go برای قاعده‌ی محدود `evidence_present`، نتیجه‌ی `pass/fail/unknown`
را به بایت‌های واقعی قاعده و شواهد متصل می‌کند. قرارداد فایل نتیجه‌ی v2 ارجاع‌های
شواهد را نگه می‌دارد و خواندن نتیجه‌های v1 حفظ می‌شود. آزمون‌های C14 شامل بازیابی
با SIGKILL واقعی، ENOSPC تزریق‌شده، replay و رد quota هستند. این قابلیت، اصالت
تولیدکننده یا جریان کامل محصول را تأیید نمی‌کند؛ اجرای OPA متعلق به C15 است.

### C15 — آداپتر محدود OPA

آداپتر داخلی Go، نسخهٔ محلی قفل‌شدهٔ OPA را برای policy موجود C04 و fact عمومی
C14 اجرا می‌کند. تصمیم به قرارداد v2 متصل می‌شود و timeout خطای صریح است؛
احراز اصالت همچنان تأییدنشده می‌ماند. این مرحله API یا UI دامنه‌ای و اجرای Rego
دلخواه اضافه نمی‌کند. برخلاف predicate داخلی C14، policy موجود OPA برای fact
فاقد مقدار طبق پیش‌فرض خود fail می‌دهد. جزئیات آزمون واقعی در شواهد C15 ثبت می‌شود.

### مرز C16

C16 بررسی داخلی و بدون state امضای Ed25519 روی بایت‌های دقیق manifest C08 است.
اعتبار امضا و تطابق هویت/کلید با سیاست اعتماد جدا هستند و موفقیت trusted به هر دو
نیاز دارد. بررسی واقعی فایل‌های ارجاع‌شده همچنان بر عهدهٔ reader موجود C08 است.
انقضا، ترتیب revision و جلوگیری از جایگزینی authority با replay باید در اولین
مسیر پذیرش stateful پیاده‌سازی و اثبات شوند؛ C16 آن‌ها را تأیید نمی‌کند.

### مرز C17

C17 فقط برابری digest موضوع در envelope موجود C07 و manifest موجود C08 را
بررسی می‌کند. `SubjectBound` به‌تنهایی اعتماد به issuer یا ادعاهای builder/source
را تأیید نمی‌کند. بررسی فایل‌ها و امضا مستقل می‌ماند؛ پذیرش پایدار revision،
تازگی و replay در اولین workflow دارای state، از جمله C20، باید اثبات شوند.
