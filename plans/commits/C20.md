## Before and after

Entry requirement: verified C19 evidence. Preserve the existing local health
listener and `--version` behavior.

The engine exposes `evaluate`, `verify` and `export` over existing C04/C14/C18/C19
contracts. The CLI distinguishes policy non-pass, invalid input and engine errors.
All generated passports remain explicitly unverified.

- `tests/fixtures/attestara/C20/`: versioned Apache-2.0 synthetic inputs, expected passport and exact fixture provenance.
- `docs/engineering/ENGINE_LAUNCH.md`, `docs/engineering/ENGINE_TESTS.md` and `docs/product/REFERENCE_WORKFLOW.md`: document commands, verification boundaries and deferred workflow obligations.

## Behavior and acceptance

- `evaluate --input PATH --policy PATH [--evidence PATH] --freshness fresh|stale` runs the existing C14 predicate, C18 caller-classified freshness and C19 passport generator. Evidence may be omitted and then remains unknown. Output is a typed C19 passport on stdout, including non-pass results.
- `verify --passport PATH` and `export --passport PATH` accept only a valid version-1 C19 passport with a matching canonical payload digest. Both emit the typed passport JSON; `verify` states on stderr that signer and bundle trust were not assessed.
- Exit codes are stable: 0 pass/success, 1 policy `fail` or `unknown`, 2 invalid arguments/input/version/digest, and 3 engine or output failure. Every command still emits a valid non-pass passport before exiting 1. Diagnostics remain bounded and do not expose raw input bytes.
- Existing loopback health and version commands remain available. No user-provided content is executed and no third-party dependency is added.

## Required negative cases

- Missing evidence and caller-classified stale evidence never become pass; policy fail and unknown remain in the emitted passport and exit 1.
- Malformed input, unsupported versions, modified passport payloads and digest mismatches exit 2 without a passport output.
- Output failure exits 3; source-like fixture text stays inert; successful policy evaluation never changes `verification: unverified`.
- Bundle byte verification, signer trust, durable revision acceptance, expiry policy and replay prevention are explicitly outside C20. The current reference workflow still requires these before C30 can certify clone-to-value.
